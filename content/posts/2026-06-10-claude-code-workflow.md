第一次让模型改这个博客的代码，它顺手把 `next.config.js` 也「优化」了一遍，理由是「更符合现代写法」。编译过了，站点也起来了，但静态导出的行为变了。

那次之后我就不再把它当补全工具用了。一个产出很快、会犯错、还会自作主张的协作者，放进工程流程得给它三样东西：规格、权限、逐 diff 的审阅。这篇记的是这套东西怎么落。

## `CLAUDE.md` 是规格，不是提示词集合

`CLAUDE.md` 放仓库根目录、随版本库走，分六块：项目约定、构建与测试命令、目录结构、明确禁止事项、代码风格、提交与审阅约定。

项目约定写语言、运行时、包管理器、产物形态；这个博客是静态导出，就写「不要引入需要服务端运行时的依赖」。命令写可直接复制的完整命令，不写「跑一下测试」。目录结构给出职责边界，尤其写清哪些目录默认不可写。明确禁止事项要具体到「不要批量重写既有文章」「不要新增依赖，除非先在计划里说明理由」。代码风格写能被工具验证的条目，如严格模式、禁用 `any`、提交信息格式。

下面是一份精简示例，命令请替换成自己仓库里的真实脚本：

```text
# 项目约定
- 语言：博客正文一律简体中文；代码注释用英文。
- 运行时：Node.js 20 LTS，包管理器 pnpm，锁定 pnpm-lock.yaml。
- 产物：静态导出，产物目录 out，不引入服务端运行时依赖。

# 构建与测试命令
- 安装：pnpm install --frozen-lockfile
- 本地预览：pnpm dev
- 类型检查：pnpm exec tsc --noEmit
- 内容校验：pnpm check:content
- 构建：pnpm build
- 单测：pnpm test -- --run

# 目录结构
- content/posts          文章源文件，一文一 slug
- src/app                App Router 页面
- src/components         可复用组件
- scripts                一次性维护脚本，需评审后才新增

# 明确禁止事项
- 不要批量重写 content/posts 里的既有文章
- 不要新增依赖，除非先在计划里说明理由
- 不要修改 src/lib 下的日期与 slug 解析逻辑，除非任务明确要求
- 不要提交 .env 或任何含密钥的文件
- 不要改动锁文件

# 代码风格与提交
- TypeScript 严格模式，禁止 any
- 组件用函数式写法，样式沿用已有 tokens，不新增 CSS 框架
- 提交信息用中文，一次提交只做一件事
```

## 上下文管理与压缩

按一个任务一个会话拆阶段，每阶段结束重述不变约束；动手前先让模型列出将要读取和改动的文件清单，确认后再执行。`@文件路径` 式引用用于精准投放，只带相关文件，不灌整库。会话变长用 `/compact` 压缩，彻底重开用 `/clear`；压缩会丢细节，关键约束写进文件，不留在会话记忆里。膨胀的信号是自相矛盾、旧方案复燃、改动范围越滚越大，出现就停手重述规格。

## 计划模式与逐步确认

大改动先走计划模式：只出方案、不动文件，计划里写清改哪些文件、分几步、每步风险。确认之后仍按执行一步、跑一次校验、看一次结果放下一步，不一次性放完。计划本身也可能错：引用不存在的脚本、误判依赖、把迁移拆得太大。具体开关名称与交互方式以官方文档为准。

## 权限边界与沙箱

默认最小权限：只读，加一份明确的命令白名单；写文件、删除、访问网络、`git push` 要显式授权。跳过权限确认的开关只在隔离环境用，不在含生产凭据的目录里开。密钥走环境变量，不进仓库也不进对话；项目级配置可评审、随仓库走，个人级配置只在本机、不提交。实验性任务放容器或 `git worktree`。权限字段名与沙箱选项各版本有调整，以官方文档为准。

## MCP 接入

接入前过五个问题：谁提供、能读什么、能不能写、凭据在哪、不可用时怎么降级。原则是只读优先、最小 scope、不给不成熟的服务写权限；项目级配置可进仓库但不能带令牌。每接一个都问它是否比一次 `rg` 更省事。具体配置文件名与添加命令以官方文档为准。

## 自定义命令、hooks、子代理各自的场景

- 自定义命令：固化步骤固定、不需判断的重复流程，如按模板新建文章、跑发布前检查清单；写一次、所有人调用结果一致，适合随仓库走。
- hooks：无论模型怎么想都必须执行的机械校验，如写文件后自动格式化、提交前跑类型检查；不该承载业务逻辑，失败难调试，且会在模型不知情时改变结果。
- 子代理：可并行且上下文应隔离的独立子任务，如同时审两个互不相关的模块、只回报结论的大范围检索；主代理只拿结论，上下文不容易膨胀。

反过来，需要结合仓库现状权衡的改动不适合塞进命令，需要人确认的策略判断不适合 hooks，需要共享主上下文的多轮讨论不适合拆给子代理。相关目录名与配置字段以官方文档为准。

## 把指令写成可验证的规格

能被验收的指令要给全四样：输入（读哪些文件、当前状态）、输出（产出什么、落到哪个路径）、约束（不许改什么、依赖什么版本）、验收条件（可执行的命令与期望结果）。

```text
任务：为 content/posts 增加发布日期格式校验。

输入：
- 读取 content/posts 下全部 .md 文件的 frontmatter
- 现有校验逻辑在 scripts/validate-posts.mjs

约束：
- 不新增第三方依赖
- 不修改任何既有文章的 frontmatter
- 改动仅限 scripts/ 与对应测试文件

输出：
- 新增校验：date 缺失或格式不是 YYYY-MM-DD 时报错并打印文件名
- 补一条对应的单元测试

验收条件：
- pnpm exec tsc --noEmit 无报错
- pnpm test -- --run 全部通过
- 手动把某篇文章的 date 改成空值，校验必须失败并打印该文件名
- git diff 审阅后，改动文件不超过 3 个
```

## 把产出纳入工程流程

几件事按顺序做。先写测试：让模型先写会失败的测试，确认它确实在测需求而非实现细节，再写实现。小步提交：一个变更一个提交，信息写为什么。逐 diff 审阅：用 `git diff` 逐个 hunk 看，优先级是配置文件、依赖与锁文件、被删除的行、新增分支条件，功能代码反而稍后看。拒绝整库重写：写进 `CLAUDE.md` 并反复执行，格式化、目录迁移、版本升级各自独立成提交，绝不与功能改动混在一起；顺手重构一下是最高风险信号。本地校验命令与 CI 一致，不过就不合并；实验改动放分支或 `git worktree`，合入前逐提交审阅，不做一次性压平合并。

## 失败模式与防线

| 失败模式 | 典型表现 | 对应防线 |
| --- | --- | --- |
| 幻觉 API | 用了不存在的方法、参数或 session 编号，还写得很确定 | 要求给出官方文档出处；不确定的写「以官方文档为准」；类型检查与编译兜底 |
| 悄悄改配置 | 顺手改了构建脚本、锁文件、环境变量或忽略规则 | `CLAUDE.md` 明确禁止；逐 diff 审阅；配置变更单独提交 |
| 上下文膨胀 | 会话越长越迟钝，旧决策复燃，改动范围越滚越大 | 分阶段执行；`/compact` 清理；关键约束落文件；必要时 `/clear` 重开 |
| 过度自信的重构 | 把能跑的代码整体重写，顺带统一风格 | 禁止整库重写；先测试后实现；限制单次改动文件数 |

## 可追溯性

每个有 AI 参与的提交都该能回答四个问题：谁下的指令、基于哪份规格、跑了哪些校验、谁审的 diff。前三个靠仓库里的文本（`CLAUDE.md`、计划文档、测试用例、验收命令），最后一个靠提交历史。提交信息里加 `AI-assisted` 标记是可选的。
