看完这届我最先想到的是两笔账：系统半透明与动态材质的铺开会让一批自定义控件的对比度和命中区域重新做回归，Foundation Models 则第一次让「端侧推理」变成一个能在业务里排期的选项。

对日常代码影响最大的三项是 iOS 19 的材质与控件刷新、Foundation Models framework 以及 Swift 6.2。

## iOS 19 与动态材质：设计语言演进，工程账要重算

iOS 19 对工具栏、标签栏、导航栏以及标准控件的动态材质做了进一步延伸，高光与背景采样的实时感更强。大多数直接用标准容器的页面不用改代码就能获得新外观；但对于自定义控件，对比度和命中区域需要重新过一遍。

材质本身半透明并随背景实时变化，如果文字、图标、分割线使用了固定的生硬颜色，在浅色与深色内容滚动混杂时容易出现可读性崩塌。把前景色换成语义色或系统材质提供的 `primary` / `secondary` 变体，并在真机上针对复杂背景滚动做对比度检查。另外，层叠效果容易在视觉上改变控件感知边界，可点击区域容易错位，务必把最小点击区域显式维持在 44pt 左右，自定义 `UIView` 复写 `point(inside:with:)` 时一定要做回归。

## Foundation Models：把端侧模型当成一个受限的系统组件

Foundation Models framework 把 Apple 的端侧基础模型暴露给 App，核心是三个东西：`@Generable`、`@Guide` 和 `LanguageModelSession`。`@Generable` 是作用于结构体或枚举的宏，编译器据其存储属性生成 schema；`@Guide` 给属性补充自然语言描述或取值约束；`LanguageModelSession` 持有指令与上下文；`SystemLanguageModel` 表示设备上的模型本身。

结构化输出下模型直接产出 Swift 值，不用正则解析自由文本。

```swift
import FoundationModels

@Generable
struct BookRecommendation {
    @Guide(description: "书名，不要带书名号")
    var title: String
    @Guide(description: "一句话推荐理由")
    var reason: String
    @Guide(description: "1 到 5 的推荐指数")
    var rating: Int
}

func recommend(for query: String) async throws -> BookRecommendation {
    let session = LanguageModelSession(
        instructions: "你是一个严谨的中文技术书荐书助手。"
    )
    let response = try await session.respond(
        to: query,
        generating: BookRecommendation.self
    )
    return response.content
}
```

关键在 `generating:` 参数把 `BookRecommendation.self` 传进去，返回值是携带 `content` 的响应对象。`@Guide` 的可用参数（描述、取值范围、元素数量等）以及 `LanguageModelSession` 初始化项的完整签名，以官方文档为准。

tool calling 把 App 能力注册成遵循 `Tool` 协议的类型，由模型在需要时决定调用。协议通常要求提供名称、描述、参数 schema 以及一个异步执行方法，会话初始化时通过 `tools:` 传入。

## 能力边界：上下文、延迟、幻觉与离线

- 上下文长度：窗口远小于服务端大模型，长文档与长对话要自己截断或分块，具体 token 上限以官方文档为准。
- 延迟：首次调用要加载权重，冷启动明显；逐 token 生成，长输出耗时近似线性增长，主线程绝不能等它。
- 幻觉：小模型在事实型问题上更容易编造，`@Guide` 只约束格式，管不了真伪。书名、日期、数值要回查本地权威数据再展示。
- 可用性与离线：完全离线、数据不出设备。但要先检查 `SystemLanguageModel.default.availability`，设备不支持、Apple Intelligence 未开启或模型未就绪时会返回不可用及原因。

降级分几层：先判可用性，再决定走端侧模型、云端接口、预置模板，还是隐藏入口。下面代码只表达分层结构，具体名称以官方文档为准。

```swift
import FoundationModels

enum RecommendSource {
    case onDevice, cloud, template, disabled
}

func route(networkReachable: Bool) -> RecommendSource {
    guard case .available = SystemLanguageModel.default.availability else {
        return networkReachable ? .cloud : .template
    }
    return .onDevice
}
```

把 prompt 做稳定哈希作为键，结构化结果落盘并带 TTL，缓存键要与 prompt 版本、schema 版本一起失效。超时必须显式做，Swift 标准库没有通用的超时包装，用任务组让推理与计时器竞争：

```swift
import Foundation

struct ModelTimeout: Error {}

func withTimeout<T: Sendable>(
    seconds: Double,
    operation: @escaping @Sendable () async throws -> T
) async throws -> T {
    try await withThrowingTaskGroup(of: T.self) { group in
        group.addTask { try await operation() }
        group.addTask {
            try await Task.sleep(nanoseconds: UInt64(seconds * 1_000_000_000))
            throw ModelTimeout()
        }
        let first = try await group.next()!
        group.cancelAll()
        return first
    }
}
```

计时任务先抛出时，`try await group.next()` 直接抛错并打断整组任务。视图消失时取消持有推理的 `Task`。

## App Intents 与 Spotlight / Shortcuts

App Intents 继续把 App 能力声明成系统可理解的实体与动作：`AppIntent`、`AppEntity`、`EntityQuery`、`AppShortcutsProvider`。系统建立索引后，Spotlight 能检索 App 内实体，快捷指令能把动作组合进自动化，Siri 也能直接调用，一份声明同时服务搜索、语音与自动化。新增的索引集成方式与具体协议名称以官方文档为准。

## Swift 6.2：approachable concurrency

模块可以配置默认 `MainActor` 隔离（Xcode 中对应 `SWIFT_DEFAULT_ACTOR_ISOLATION` 构建设置，取值以本机为准），单线程的 UI 代码默认就安全；需要真正并行的函数用 `@concurrent` 显式标注。迁移的麻烦在于默认隔离会改变既有 `nonisolated` 的语义，第三方库和老代码得逐个核对，Swift Evolution 提案编号与最终语义以官方为准。

## Xcode 17 的开发辅助能力

Xcode 17 把编码辅助进一步集成进编辑器：基于模型的补全、跨文件修改建议、文档与测试的生成，以及更直接的错误解释。生成代码都要过编译、评审与可追溯性检查。具体功能名称与开关位置以官方文档为准。

## 我的判断

按「现在能不能排进排期」分成三档：

| 项目 | 判断 | 理由 |
| --- | --- | --- |
| App Intents 接入 Spotlight 索引 | 值得立即采用 | 一份声明复用多入口，改造范围可控，回归成本低 |
| `@Generable` 结构化输出 + 可用性检查 + 超时 | 值得立即采用 | 替代脆弱的文本解析，离线与隐私收益明确，降级链路可自测 |
| Swift 6.2 默认 MainActor 隔离（新模块） | 观察 | 新项目收益大，存量模块需先盘点 `nonisolated` 假设 |
| 端侧模型生成事实型内容 | 观察 | 幻觉与上下文受限，必须外挂权威数据源校验 |
| 全面重做自定义控件的动态材质 | 暂缓 | 材质动态、对比度与命中区域需大量真机回归，等官方适配指南稳定 |
| 用端侧模型完全替代云端推理 | 暂缓 | 上下文与能力差距明显，适合做离线兜底而非主链路 |
