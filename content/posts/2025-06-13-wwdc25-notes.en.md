WWDC25 left me with two practical bills to pay. The new translucent, dynamic materials make custom controls worth testing again for contrast and hit-area regressions. At the same time, Foundation Models makes on-device inference something an app can schedule, constrain, and fall back from.

## The three changes most likely to affect daily work

The first is iOS 19's dynamic materials and controls. Toolbars, tabs, navigation bars, and standard controls now adapt more actively to their surroundings. Custom controls should use semantic colors, preserve primary and secondary contrast, and be tested on real devices rather than only in a static screenshot. Keep interactive areas around the familiar 44-point minimum; for a custom `UIView`, `point(inside:with:)` can expand the touch target without changing the visual bounds.

The second is the Foundation Models framework. `@Generable` and `@Guide` describe a structured result, while `LanguageModelSession` and `SystemLanguageModel` provide the session and availability checks. The response is returned as a Swift value instead of a JSON string that the app has to parse again:

```swift
import FoundationModels

@Generable
struct BookRecommendation {
    @Guide(description: "Book title, without quotation marks")
    var title: String
    @Guide(description: "A one-sentence reason to recommend it")
    var reason: String
    @Guide(description: "A rating from 1 to 5")
    var rating: Int
}

func recommend(for query: String) async throws -> BookRecommendation {
    let session = LanguageModelSession(
        instructions: "You are a careful assistant that recommends technical books."
    )
    let response = try await session.respond(
        to: query,
        generating: BookRecommendation.self
    )
    return response.content
}
```

Tools can be exposed through the `Tool` protocol. Give each tool a name, description, and schema, implement its asynchronous `execute` method, and pass the tools to the session. This is useful for bounded actions, but it does not make a model's answer authoritative: a `Guide` constrains the shape of a result, not the truth of its content.

The framework still has real limits. Context is smaller than that of many server models, and cold starts, latency, streaming behavior, device support, and offline availability all matter. Check `SystemLanguageModel.default.availability`, add a timeout, and provide a fallback such as a template, a cloud service, or a disabled feature. A throwing task group is enough to race generation against a timeout and cancel the losing task.

The third change is Swift 6.2's more approachable concurrency model. New modules can opt into default `MainActor` isolation with `SWIFT_DEFAULT_ACTOR_ISOLATION`; use `@concurrent` when work must genuinely run in parallel, and audit `nonisolated` code instead of adding it mechanically.

## App Intents and coding assistance

`AppIntent`, `AppEntity`, `EntityQuery`, and `AppShortcutsProvider` remain the practical route into Spotlight, Shortcuts, and system-level actions. If an action or entity is useful outside the app, describe it with these APIs so the system can index and invoke it.

Xcode's coding assistance is helpful for scaffolding and repetitive edits, but generated code still needs to compile, be reviewed, and be traced through the app's actual behavior.

## A conservative adoption order

| Topic | Recommendation |
| --- | --- |
| App Intents and Spotlight | Adopt now |
| `@Generable` with availability checks and timeouts | Adopt now |
| Default `MainActor` isolation in new Swift 6.2 modules | Observe and measure |
| On-device factual generation | Observe; validate against authoritative sources |
| A wholesale custom-material redesign | Postpone until real-device testing is complete |
| Replacing cloud inference everywhere | Postpone until capability and latency data are clear |

The useful lesson from WWDC25 is not to add a model everywhere. It is to make each new capability bounded: define the result, check availability, set a timeout, and keep a non-model path that still works.
