## The Swift 5.9 macro system

Macros are either freestanding or attached. `@freestanding` produces an expression or declaration such as `#stringify`; `@attached` adds members, accessors, peer declarations, attributes, or conformances. Implementations use `swift-syntax` in a separate compiler-plugin target and are referenced with `#externalMacro`.

```swift
@freestanding(expression)
public macro stringify<T>(_ value: T) -> (T, String) =
    #externalMacro(module: "MyMacros", type: "StringifyMacro")

let (value, text) = #stringify(1 + 2)
```

Macros are useful for boilerplate such as `Codable` members, accessors, and protocol conformances. The cost is a plugin target, strict `swift-syntax` version matching, and debugging expanded code rather than the source spelling. For a small team, saving a few lines may not justify the machinery.

## Smaller syntax and experimental ownership

Optional binding can be written `if let name`; that shorthand predates Swift 5.9. Swift 5.9 adds `if` and `switch` expressions, which can directly produce a value. Branches must be exhaustive and have a common result type.

Noncopyable types arrived in Swift 5.9 as an experimental feature. The spelling, ownership rules, and interaction with generics continued to evolve, so I treated them as something to understand, not something to put into production.

## SwiftData versus Core Data

SwiftData uses `@Model` for model classes, `ModelContainer` for storage, and `@Query` in SwiftUI views. Core Data remains the mature object-graph framework, with years of migration, performance, and debugging experience.

SwiftData is a good starting point for a new, simple, SwiftUI-first project whose deployment target can move forward. A project with a complicated Core Data stack, manual migrations, fine-grained fetched-results controllers, or old OS support has no reason to migrate automatically. The migration paths are not equivalent.

## Observation and `@Observable`

Observation tracks the properties a view actually reads. The older `ObservableObject` approach requires `@Published` on each mutable property; `@Observable` lets the macro generate tracking and often replaces `@StateObject` with `@State`.

The new model has deployment-target constraints and does not simply carry over every `objectWillChange` and Combine subscription. Both systems can coexist, but keeping one model inside a view tree makes refresh bugs easier to reason about.

## Other updates

`#Preview` makes previews compile-time declarations. `ContentUnavailableView` supplies standard empty states. `scrollTargetLayout` and `scrollTargetBehavior` simplify aligned paging. TipKit provides `Tip`, `TipView`, and `popoverTip`. MapKit adopts more declarative entry points for camera position, annotations, and styles. visionOS adds a new SDK and spatial-computing target.

## What I would migrate now

| Feature | Decision | Reason |
| --- | --- | --- |
| `#Preview` | Now | Preview-only and easy to roll back |
| Optional-binding and `if`/`switch` expressions | Now | Local syntax with compiler protection |
| `@Observable` | New modules now; old modules selectively | Deployment and model-boundary constraints |
| TipKit and new MapKit APIs | As needed | Depends on the product's OS baseline |
| SwiftData | Wait | Migration is not equivalent to Core Data |
| Custom macros | Wait | Plugin and `swift-syntax` maintenance cost |
| Noncopyable types | Wait | Early experimental semantics |

I would separate syntax changes, preview changes, and Observation migration into different commits. Before touching the data layer or deployment target, I would make the existing regression suite green.
