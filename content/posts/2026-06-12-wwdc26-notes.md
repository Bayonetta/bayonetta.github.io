这篇只记 Apple Developer 官方 What's New 和发布说明能确认的东西，不写具体 API 签名，也不写 session 编号。beta 期的信息一律以官方文档为准。

## 能确认的事实

- 主题演讲时间是 2026 年 6 月 8 日，太平洋时间。
- 官方 What's New 页面列出 Xcode 27，以及 iOS 27、iPadOS 27、macOS Tahoe 27、tvOS 27、visionOS 27、watchOS 27 等平台更新。
- Swift 6.4 的官方资料提到面向全平台统一可用性标注的 `anyAppleOS`，以及 `@diagnose` 等语言和工具链更新。具体能力与可用版本仍以发布说明为准。
- Xcode 27 的编码智能、Agent 工作流和配套的专家指导是这一代工具链的关注焦点。
- SwiftUI 有独立的新功能专题。

就这些。剩下的是判断，不是事实。

## 拿到 beta 先别急着编

用 Xcode 27 Beta 编出来的产物不能直接当作正式发布版本，beta SDK 里的符号在用户设备上未必存在。这条每年都一样，但每年都有人踩。

| 维度 | 观察项 | 动作 |
| --- | --- | --- |
| 部署目标 | 最低系统版本是否随新 SDK 上移 | 保持旧基线，用 `available` 条件隔离新路径 |
| SDK 基线 | beta 与稳定版 SDK 的差异清单 | 主分支用稳定版，beta 只在独立分支验证 |
| 工具链 | Xcode 27 Beta 与 Swift 6.4 的对应关系 | 记录确切版本号，写入 CI 镜像 |
| 依赖 | 第三方库是否已适配新工具链 | 逐个锁定版本，未适配的先隔离 |

`available` 判断要配合编译条件用。主分支只走稳定工具链，新 SDK 的验证放在随时可以丢掉的分支上——最怕的是 beta 行为被悄悄带进发布产物，等用户反馈异常才发现。

## Agent 进了工具链，评审对象就变了

Xcode 27 把编码智能和 Agent 工作流放到了工具链中心。这件事对日常工作的影响，不在「能不能生成代码」，而在评审要看什么。

以前看人写的 diff，问的是「这段逻辑对不对」。现在还得先回答三个问题：这段改动是谁的决策、依据哪份上下文、能不能复现。

我的做法是把 Agent 的改动单独成提交，提交信息写明任务描述和所用上下文，跟人工改动分开。生成代码和人工代码走同一套门槛——编译、静态检查、单测，并发与内存所有权照样人工复核，不因为它是模型写的就放宽。可追溯性靠可复现的输入：prompt、相关文件快照、工具链版本一起归档，别只留一份聊天记录。

具体功能名称、交互方式和 beta 阶段的变化，以官方文档为准。

## 一次只动一个变量

迁移的时候，每个动作只改一处：只升工具链、只改一处并发标注、只换一个 API，然后立刻跑一组固定的回归用例。

回归集我按三层组织。编译层看全模块能不能干净编译、有没有新增警告；行为层跑核心路径的单测与 UI 测试；兼容层在最低部署目标的设备上跑一遍关键流程。每层的基线结果存档，升级前后做差分。

对 Swift 版本变化尤其要盯语义级改动。默认隔离、并发标注、存在类型与不透明类型的推导，这几处都可能在完全不报错的前提下改变行为。编译过了不等于行为没变。

## 选型清单

新 SDK 出来先观察一个周期，别急着改 `Package.swift`。我会过一遍这几条：

- 新能力是不是只能用新 SDK 实现，旧路径能不能用可用性条件优雅退化；
- 部署目标上移的代价：会丢掉多少现存设备，有没有数据支撑；
- 依赖树里有多少库还没适配，等待成本可不可控；
- CI、打包与签名链路要不要同步升级，镜像能不能回滚；
- 评审与追溯流程覆盖不覆盖 Agent 生成的改动；
- 有没有一组能自动跑的回归用例，证明升级没改变行为。

跨大版本时先在独立 target 里做技术验证，等稳定版发布、依赖跟上、回归基线齐了再合入。
